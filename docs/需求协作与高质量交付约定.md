# 需求协作与高质量交付约定

> 来源：飞书转存扩展「高保真转存」多轮返工复盘（约消耗当周 Cursor token 34%）。  
> 目的：把「看起来简单、做起来反复」的坑说清楚，并约定以后怎么提需求、怎么验收，减少无效沟通。

---

## 一、这次复盘：为什么这么费劲？

### 1.1 「简单」是错觉

口头目标往往是一句话，例如：

> 转存后跟原文一样。

但对飞书（尤其是**禁止复制**的文档）来说，「一样」至少可能包括：

| 维度 | 实际容易踩的坑（本次已踩过） |
|------|------------------------------|
| 文档标题 | 课名 vs 正文某个章节 h1 |
| 字色 / 高亮 | 标题红字、代码块**按行**红字（`textHighlight`） |
| 链接 | mention、外链、**drive-stream 预览链**（不是 file 块） |
| 附件 | 真 file/view 块 vs 正文里的可点 PDF 名 |
| 路径 | 能原生复制 vs 只能高保真重建 |
| 导入器 | `parse_html` 吃什么、剥什么 |

对你是「保真」；若没拆成可验证清单，AI 容易理解成「能转过去 + 字数差不多」。**复杂度被双方同时低估了。**

### 1.2 AI 侧的主要问题（本次占大头）

1. **先改代码、晚对原文档**  
   真根因多在源文档 DOM / 数据里（颜色 class、预览链形态等）。更早打开你给的原文/转存后链接对照，本可少好几轮。

2. **用猜的故障修真的故障**  
   例如链接按「附件块上传」修，实际是正文 `internal-api-drive-stream` 预览链被导入器剥掉。方向错了仍发版，你被迫当回归测试员。

3. **自测只证明「写了」，不证明「对了」**  
   断言「有某个函数 / 某段字符串」≠ 对照金样本页面验收通过。

4. **过早宣称修好**  
   未在真实样本上验证就交付，直接烧时间和 token。

5. **过程噪声**  
   无关文案、过严/过松门禁来回拧，消耗轮次却不推进你要的结果。

### 1.3 协作上放大成本的点

- 验收标准滞后：先有「要一样」，后靠截图才钉死「标题色 / PDF 链 / 代码红字」。
- 禁止复制场景不能靠「原生复制」蒙混，必须走重建，坑在飞书私有结构与导入能力。
- 对话式修 bug 适合探索，不适合「每版必过真实对照」——缺硬规矩时就会多轮熬。

### 1.4 为什么 token 会很贵

典型坏循环：

```text
猜原因 → 改一大片 → 弱自测通过 → 宣称修好 → 你实测失败 → 再截图纠偏 → 再猜…
```

**贵的不是需求本身，是错误假设被交付了多次。**

### 1.5 一句话结论

需求表面简单，实际是禁复制下的高保真重建。费劲主因是：把「能转存」当成「转得像」，又用错因修、用弱测试放行，让你用真人验收补了本该 AI 做的取证和把关。

## 二、以后提需求：你怎么说，我才能一次做对

下面按**你提需求时的推荐步骤**写。不必每次写长文，但**关键格子尽量填齐**；缺得越多，返工概率越高。

### 步骤 0：先判断需求类型（30 秒）

| 类型 | 例子 | 沟通重点 |
|------|------|----------|
| A. 观感/保真 | 转存后颜色、链接、布局要像原文 | **金样本链接 + 截图对比 + 验收清单** |
| B. 功能行为 | 按钮、流程、失败提示 | 操作路径 + 期望/实际 |
| C. 纯重构/清理 | 删文案、改名、拆文件 | 范围边界（改哪些、不改哪些） |
| D. 探索未知 | 「某能力为什么能做到…」 | 明确只要结论还是要落地改代码 |

今天这类问题属于 **A**。A 类最忌「先开干再对图」。

---

### 步骤 1：用固定模板开需求（复制即用）

把下面模板填进对话（可删无关行）：

```markdown
## 目标（一句话）
（例：禁止复制的课文档，转存后观感与原文一致，可点链接不丢。）

## 类型
A 观感保真 / B 功能 / C 清理 / D 探索

## 金样本（必填，A/B 强烈建议）
- 原文链接：
- 转存后链接（若已有失败结果）：
- 扩展版本号：（例 v2.28.6）
- 转存方式：（原生复制 / 高保真重建 / 不确定）

## 验收清单（必须可勾选、可对图）
- [ ] …
- [ ] …
- [ ] 明确「不要求」的项：…（例：水印、权限条、画板实况）

## 证据（有就贴）
- 原文截图：
- 转存后截图：（同一区域并排最好）
- 红框标出的差异点：（用文字再写一遍，防截图歧义）

## 约束
- 不要出现的第三方品牌/文案：
- 是否允许升版本号：
- 未过金样本是否禁止宣称「已修好」：是（默认）

## 完成定义
只有验收清单全部勾上，且 AI 已对照金样本自检，才算交付。
```

**你少写一句「看起来要一样」，多写三条可勾选项，通常比多聊五轮更省 token。**

---

### 步骤 2：给「金样本」，不要只给抽象描述

请尽量同时提供：

1. **原文 URL**
2. **转存后 URL**（若已有坏结果）
3. **同一区域的前后截图**（标题区、链接区、代码块等）
4. **用一句话点名差异**（例：「代码块里除第一行外应是红字，转存后全黑」）

没有链接时，至少要有：失败现象 + 版本号 + 关键区域截图。

---

### 步骤 3：把「一样」拆成验收清单（避免范围漂移）

建议按维度列，并标明优先级：

**P0（不做完不算交付）**

- 例：PDF/跳转链接可点且不是纯文本  
- 例：指定代码块红字保留  
- 例：文档标题为课名而非章节名  

**P1（本轮尽量做）**

- 例：标题字色 `#d83931`  
- 例：外链保留  

**明确不做（Out of scope）**

- 例：水印、评论、权限提示条、画板/多维表实况  

没有 Out of scope 时，AI 容易无限「再保真一点」，轮次爆炸。

---

### 步骤 4：约定交付门禁（你可直接要求 AI 遵守）

以后你可以在需求末尾加一句硬性要求（推荐原样粘贴）：

> **交付门禁：**  
> 1）先对金样本取证（DOM/结构/颜色/链接形态），再改代码；  
> 2）自测必须包含「能复现本次失败」的用例；  
> 3）未对照金样本验证通过前，禁止说「已修好」；  
> 4）每版只声称通过验收清单里已勾且已验证的项。

这样可以把「你当测试员」的角色，压回「AI 先自证，你终验」。

---

### 步骤 5：一次只锁一轮主目标（并行会乱）

- 同一轮优先：**1 个 P0 主题**（如「链接」或「代码块颜色」），附带最多 1～2 个强相关项。  
- 不要在同一轮里同时开：标题策略 + 全站样式门禁 + 品牌文案 + 大重构。  
- 上一版 P0 未过，不叠加新的大需求。

---

### 步骤 6：反馈失败时怎么说（最短、最有效）

不要只说「还是不对」。请用：

```markdown
版本：vX.Y.Z
金样本：原文 … / 转存后 …
哪一条验收失败：（直接引用清单条目）
证据：截图 / 红框位置
期望：…
实际：…
```

一条失败对应一条反馈，AI 才能对准修，而不是重新猜整锅。

## 三、AI 侧必须遵守的工作流（给你核对用）

你可以把本节当成「对方有没有偷懒」的检查单。

### 3.1 开工前（改代码之前）

1. 复述目标与验收清单（用你的原文，不擅自扩 scope）  
2. 打开金样本链接或根据截图列出**可证伪**的技术假设  
3. 标明：先取证 / 再实现 / 再金样本验证  

若跳过 2、3 直接改大文件 → 高风险，可要求停下。

### 3.2 实现中

1. 根因要能对应到证据（class、href 形态、导入行为等）  
2. 回归测试要绑失败样本（例如 drive-stream→`/file/`、代码行 `#d83931`）  
3. 用户可见文案不含第三方商业品牌名  

### 3.3 交付时（宣称完成前）

1. 列出：改了什么、对应哪几条验收  
2. 给出自测结果（命令 + 通过数）  
3. **写明尚未验证 / 做不到的边界**（诚实，不拿「基本完成」糊弄）  
4. 未过金样本对照 → 只能说「待你终验」，不能说「已修好」

## 四、推荐沟通话术（可直接复制）

### 4.1 新开保真类需求

```text
按《docs/需求协作与高质量交付约定.md》执行。

目标：…
金样本原文：…
金样本转存后（如有）：…
验收 P0：
- [ ] …
- [ ] …
不要求：…

交付门禁：先取证再改代码；不过金样本相关自检不许说已修好。
```

### 4.2 打回某一版

```text
vX.Y.Z 未通过验收「…」。
原文：… 转存后：…
截图已附。期望…，实际…。
请先取证再改，修好后只声称这一条，并跑回归。
```

### 4.3 控制范围

```text
本轮只做 P0 的链接问题，颜色/标题先不动。
Out of scope：水印、画板。
```

## 五、你可减少的投入（但不建议省的）

| 可省 | 不建议省 |
|------|----------|
| 长篇背景故事 | 金样本链接 |
| 重复粘贴整段聊天 | 前后截图 + 一句差异说明 |
| 每次解释飞书是什么 | 验收清单 P0 / 不要求 |
| —— | 版本号与失败条目 |

**最小有效输入** ≈ 模板里的：目标 + 金样本 + 3 条 P0 + 截图差异一句话。

## 六、避免再次出现「今天这种情况」的检查表

提需求前：

- [ ] 我写了可勾选的验收清单，而不只是「要一样」  
- [ ] 我给了原文（和失败的转存后）链接或等价证据  
- [ ] 我标明了不要求的范围  
- [ ] 我要求了交付门禁（先取证、未验证不说修好）  

收交付前：

- [ ] AI 是否复述了验收清单  
- [ ] AI 是否展示了针对失败样本的自测  
- [ ] AI 是否诚实写了做不到的边界  
- [ ] 我是否用金样本终验，而不是听「应该好了」

## 七、和本仓库的关系

- 本文件服务本扩展的需求协作；**不替代**具体功能设计文档。  
- 技术实现仍以代码与自测为准；本文件管的是**怎么提、怎么验、怎么算做完**。  
- 若希望 AI 每次自动遵守，可将本文件要点再做成 Cursor Rule（`.cursor/rules/`）；需要的话可单独说一声再加。
